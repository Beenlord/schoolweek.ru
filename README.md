# Lemonade 🍹

Школьный дневник — это гениальное изобретение! Им было удобно пользоваться в школе, некоторые продолжают им пользоваться
в вузе, а мы решили создать электронную версию такого дневника для обычной жизни. Наш дневник сочетает в себе
ностальгические нотки школьного прошлого, а так же простоту и гениальность расписания всё в одном и концепцию «неделя на
одном листе».

## Концепция

За основу взят разворот бумажного школьного дневника:

- Слева — понедельник, вторник, среда.
- Справа — четверг, пятница, а ниже — суббота и воскресенье: визуально одна общая клетка (как в бумажном дневнике),
  но фактически две независимые клетки меньшей высоты, каждая под свой день.

```
┌───────────┬───────────┐
│ Пн        │ Чт        │
├───────────┼───────────┤
│ Вт        │ Пт        │
├───────────┼───────────┤
│           │ Сб        │
│ Ср        ├───────────┤
│           │ Вс        │
└───────────┴───────────┘
```

Каждый день — не набор отдельных строк-полей, а единое разлинованное текстовое поле с переносами, куда пользователь
пишет дела в свободной форме с лёгкой markdown-разметкой (списки, выделения и т.п.), которая сразу рендерится
отформатированной — пользователь не видит «сырой» markdown-синтаксис. В превью будничной клетки видно первые ~6 строк
дня, а в клетках Сб и Вс — по ~3 строки каждая (клетка вдвое ниже); строки не переносятся — если строка не помещается
по ширине клетки, она обрезается, а не переносится на следующую. Клик по клетке дня открывает его в отдельном окне
для просмотра и редактирования всего содержимого целиком.

Сверху страницы — текущие год, месяц и номер недели; текущий день в сетке визуально выделен. Переключаться между
неделями (в прошлое и в будущее) можно двумя способами: свайпом «неделя назад / неделя вперёд», либо кликом по
году/месяцу — по клику открывается список недель для перехода к произвольной.

## ТЗ (MVP)

### Модель данных

- **Неделя** — определяется датой понедельника (началом недели), явно как сущность не хранится, а вычисляется.
- **День** — `(userId, date)` → одно текстовое поле с содержимым в markdown. Один день = один документ, без деления
  на подстроки/задачи — переносы строк и разметка внутри поля свободные, парсер их не структурирует.
- Сб и Вс — это два разных дня с двумя разными датами и двумя независимыми клетками в сетке, отдельными от будних
  дней только уменьшенной высотой превью.

### Пользователи и аутентификация

- **Пользователь** — `name`, `email` (уникальный, служит логином), `password` (хеш), `timezone`, секретный вопрос +
  ответ (для восстановления пароля). Фамилия и прочие поля не нужны — дневник полностью личный, никому кроме
  владельца не показывается.
- Регистрация: обязательны `name`, `email`, `password`, `timezone` (поле предзаполняется автоопределением на
  клиенте, пользователь может его поправить вручную), секретный вопрос из предложенного списка + ответ на него.
- Авторизация: `email` + `password`.
- Восстановление пароля: без email-рассылки — пользователь вводит `email`, отвечает на свой секретный вопрос и,
  если ответ верный, задаёт новый пароль. Верификация email на этапе MVP не нужна.
- Список секретных вопросов — контент, который нужно будет придумать отдельно (не часть этого ТЗ).
- Сама аутентификация (регистрация/вход/выход/восстановление) реализуется через Inertia — обычные серверные роуты
  и контроллеры с сессией (`web`-guard), без выдачи токена на руки пользователю. Sanctum нужен не для этого, а для
  API-запросов — либо от внешних потребителей, либо для внутренних AJAX-вызовов самого приложения в процессе
  работы (например, сохранение дня без полной перезагрузки страницы) поверх той же сессии.

### Страницы

MVP состоит из шести базовых страниц — все реализованы как Inertia-компоненты (`resources/js/Pages/*.vue`),
рендерятся из соответствующих контроллеров на `web`-роутах:

| Роут | Доступ | Назначение |
| --- | --- | --- |
| `/` | публичный | Домашняя — посадочный лендинг с питчем продукта (см. вступление README) и переходом на регистрацию/вход. |
| `/register` | публичный (авторизованного редиректит на `/now`) | Регистрация — форма из раздела «Пользователи и аутентификация» выше. |
| `/login` | публичный (авторизованного редиректит на `/now`) | Авторизация — `email` + `password`, ссылки на `/register` и на восстановление пароля. |
| `/forgot-password` | публичный (авторизованного редиректит на `/now`) | Восстановление пароля — один компонент с локальным состоянием на три шага: email → секретный вопрос → новый пароль. Отдельный роут (а не часть `/login`), чтобы на него можно было перейти напрямую по ссылке. |
| `/now` | только авторизованным (редирект на `/login`) | Календарь — основной экран приложения, сетка недели; подробности ниже в «Экран «Неделя»». |
| `/me` | только авторизованным (редирект на `/login`) | Профиль — просмотр и редактирование своих данных; подробности ниже в «Профиль». |

`/now` и `/me` — единственные страницы за авторизацией, у них общий элемент интерфейса (шапка/навигация) со
ссылкой на профиль и кнопкой выхода.

### Экран «Неделя» (`/now`)

- Сетка 2×3: слева Пн/Вт/Ср (равной высоты), справа Чт/Пт/Сб/Вс, где Сб и Вс — две клетки вдвое ниже обычных.
- Каждая клетка — превью дня: заголовок (день недели + дата) и первые строки содержимого без скролла внутри клетки
  (~6 строк для Пн–Пт, ~3 строки для Сб и Вс).
- Текущий день визуально выделен в сетке.
- Шапка страницы показывает год, месяц и номер текущей отображаемой недели. Номер недели отсчитывается от начала
  месяца (а не как ISO-номер недели года); неделя, разбитая между двумя месяцами, целиком принадлежит тому месяцу,
  в котором больше её дней.
- Переключение недель: свайп «вперёд/назад» на одну неделю; клик по году/месяцу в шапке открывает пикер недель —
  мини-календарь, где вместо дней ячейки в формате `[число–число]`, каждая ячейка — целая неделя, клик по ней
  переключает на неё. «Текущая неделя» — состояние по умолчанию при открытии.

### Редактирование дня

- Клик по клетке дня открывает модальное окно/отдельный экран с полным содержимым этого дня.
- В окне — единое разлинованное текстовое поле (визуально имитирует тетрадный лист), где markdown-разметка
  рендерится сразу по ходу ввода (WYSIWYG, без отображения «сырого» синтаксиса); переносы строк свободные, без
  ограничения по числу строк — лимит на количество видимых строк действует только в превью на сетке недели.
- Автосохранение по мере ввода или явная кнопка «Сохранить» — конкретика на усмотрение реализации.
- Просмотр и редактирование используют один и тот же компонент (нет отдельного read-only режима).

### Профиль (`/me`)

- Просмотр и редактирование собственных данных пользователя: `name`, `email`, `timezone`, секретный вопрос/ответ
  (можно сменить), смена пароля (требует ввода текущего пароля).
- Кнопка выхода — завершает сессию, редиректит на `/`.
- Дополнительных полей (аватар, настройки и т.п.) в MVP нет — только то, что уже есть в модели пользователя.

### Вне рамок MVP

- Совместное использование дневника несколькими пользователями, шаринг недель.
- Напоминания/уведомления.

## Сущности

Персистентных сущностей в приложении две — `User` и `Day`; всё остальное («Неделя», «Месяц») — производные
значения, вычисляемые из `date`, а не отдельные таблицы.

### User

| Поле | Тип | Обязательное | Примечание |
| --- | --- | --- | --- |
| `id` | integer | — | первичный ключ |
| `name` | string | да | только имя, без фамилии |
| `email` | string | да | уникальный, служит логином |
| `password` | string (hash) | да | хешируется как обычно |
| `timezone` | string | да | IANA-идентификатор (`Europe/Moscow` и т.п.); автоопределяется на клиенте при регистрации, пользователь может поправить вручную; валидируется по реальному списку зон, а не произвольная строка |
| `secret_question` | string | да | один из предложенного набора вопросов (контент набора — вне этого ТЗ) |
| `secret_answer` | string (hash) | да | ответ на секретный вопрос, хешируется так же, как пароль — не хранится в открытом виде |
| `created_at` / `updated_at` | timestamp | — | стандартные Laravel-таймстемпы |

Один `User` — владелец произвольного количества `Day`; связи с другими пользователями нет (шаринга нет, см. «Вне
рамок MVP»).

### Day

| Поле | Тип | Обязательное | Примечание |
| --- | --- | --- | --- |
| `id` | integer | — | первичный ключ |
| `user_id` | integer (FK → `users.id`) | да | владелец дня |
| `date` | date | да | календарная дата дня (не день недели — суббота и воскресенье это два разных `Day` с разными `date`) |
| `content` | text | нет | markdown-текст дня; пустой/`null`, пока пользователь ничего не написал — клетка при этом всё равно рендерится, просто пустая |
| `created_at` / `updated_at` | timestamp | — | стандартные Laravel-таймстемпы |

Уникальный индекс — `(user_id, date)`: на пару пользователь+дата не может быть больше одной записи. История версий
не хранится (см. «Вне рамок MVP») — обновление `content` просто перезаписывает текущее значение.

### Производные понятия (не таблицы)

- **Неделя** — Пн–Вс, вычисляется от даты понедельника; на экране `/now` это семь `Day` (реальных или ещё не
  созданных) пользователя, лежащих в этом диапазоне дат.
- **Месяц/номер недели в шапке** — тоже вычисляется на лету по правилу «неделя принадлежит месяцу, в котором
  большинство её дней» (см. «Экран «Неделя»» выше), отдельно нигде не хранится.

## Технический стек

### Уже есть и работает

- **Backend**: Laravel 13 на PHP 8.4, `vendor/`, `artisan` и базовая структура приложения на месте.
- **Auth-пакет**: `laravel/sanctum` установлен и сконфигурирован (токен-based API-аутентификация), но без единой
  строчки прикладного кода поверх — ни модели `User`, ни контроллеров, ни роутов.
- **API-документация**: `dedoc/scramble` генерирует OpenAPI по роутам/валидации, отдаётся на `/docs/api`.
- **Frontend**: `inertiajs/inertia-laravel` + Vue 3, полностью собранный build-тулинг — `vite.config.js` (плагины
  `laravel-vite-plugin`, `@vitejs/plugin-vue`, алиас `@` → `resources/js`), `jsconfig.json` с тем же алиасом,
  npm-скрипты `dev`/`build`.
- **База данных**: MariaDB (не sqlite по умолчанию Laravel).
- **Кэш/очереди/сессии**: Redis для кэша и очередей; сессии — на `database`-драйвере.
- **Инфраструктура**: трёхстадийный `Dockerfile` (base-образ с PHP-расширениями → vendor → финальный), `compose.yml`
  с сервисами `app`/`mariadb`/`redis` и health-check-гейтингом, `entrypoint.sh` гоняет миграции и поднимает очередь/
  шедулер при каждом старте контейнера.

### Чего не хватает для реализации MVP

**Данные и бэкенд**

- Миграция и модель `User` — сейчас нет вообще ни одной модели в `app/Models`. Нужны поля `name`, `email`,
  `password`, `timezone`, `secret_question`, `secret_answer` (ответ на секретный вопрос стоит хранить хешированным,
  как пароль, а не в открытом виде).
- Миграция и модель для дня (`schedule`/`days`): `user_id`, `date`, `content` (markdown-текст), уникальный индекс
  по `(user_id, date)`.
- Контроллеры и роуты аутентификации (`routes/web.php`, Inertia): регистрация, логин/логаут на сессии, восстановление
  пароля по секретному вопросу (запросить вопрос по email → проверить ответ → задать новый пароль).
- Контроллеры и роуты (`routes/api.php` сейчас пустой) для данных дневника: получение/сохранение дня, получение
  недели целиком — используются внутри уже авторизованного Inertia-приложения (AJAX поверх сессии), а не как
  самостоятельный публичный API.
- Серверная логика расчёта границ недели/месяца и номера недели по правилу «большинство дней» — нетривиальная
  логика на стыке месяцев, нужна отдельная функция/сервис с тестами.
- **Санитизация markdown при рендере** — раз пользовательский контент рендерится как форматированный текст
  (потенциально в HTML), нужна защита от XSS при сохранении/выводе, а не просто хранение сырой строки.
- Валидация `timezone` по списку реальных идентификаторов (PHP: `DateTimeZone::listIdentifiers()`), а не
  произвольная строка с клиента.

**Frontend**

- Библиотека для WYSIWYG-редактирования markdown — в `package.json` сейчас нет ни одного markdown-редактора
  (кандидаты: Tiptap с markdown-расширением, Milkdown и т.п.), нужно будет выбрать и завести отдельно.
- Вообще отсутствует какой-либо CSS-тулинг (`resources/css` нет, Tailwind/UnoCSS не установлены) — учитывая
  «тетрадный», дизайн-специфичный стиль интерфейса, стоит решить, писать ли вручную SCSS/CSS или подключать
  утилитарный фреймворк.
- Компоненты пяти страниц из раздела «Страницы» (`Register`, `Login`, восстановление пароля, `Now`/«Неделя», `Me`/
  «Профиль») плюс общая шапка/навигация для авторизованных страниц — сейчас есть только пустой `Home.vue` под
  лендинг.
- Обработка свайпов для переключения недель — потребует либо самописного touch/pointer-обработчика, либо лёгкой
  библиотеки жестов.

## Сборка

Сейчас можно собрать и опубликовать только базовый образ (`base`-стейдж `Dockerfile`) — он содержит PHP 8.4-FPM
на Alpine с нужными расширениями (redis, imagick, gd, intl, pdo_mysql и т.д.), composer и пользователя `www`.
Он публикуется в Docker Hub под тем же namespace, что уже используется в `Dockerfile` как основа для стейджей
`vendor` и финального (`vovikko/alpine-php-fpm`).

```bash
# Собрать образ из base-стейджа
docker build --target base -t vovikko/alpine-php-fpm:8.4 .

# Авторизоваться в Docker Hub (один раз)
docker login

# Опубликовать образ
docker push vovikko/alpine-php-fpm:8.4
```

Тег версии (`8.4`) должен совпадать с тем, что указан в `Dockerfile` в `FROM vovikko/alpine-php-fpm:8.4` для
стейджей `vendor` и финального — иначе последующая сборка приложения будет тянуть образ, не содержащий изменений
из `base`.
